State Management and Persistence

Status: done

This section ports the State Management portion of Technical Design (section 4 of the GDD). It describes where game state lives, how the UI reads it, how it is persisted, when it is saved, and how it is mirrored for headless testing.

Data Models (Zod Schemas)

Ship
x, y, rotation, velocityX, velocityY
Upgrades
blaster: number, collector: number, storage: number
Cargo
scrap: number, fragments: number, silver: number, gold: number, capacity: number
GameState
ship, upgrades, cargo, hp, timestamp

State Management

Game state lives in the Three.js render loop (60fps)

The authoritative game state lives in the Three.js render loop running at 60fps. The simulation advances each frame through the shared tick function.

React state for UI/HUD via the useGameState hook

React state for the UI and HUD is managed via the useGameState hook. The hook owns paused state, scrap, cargo, upgrades, and player HP, and exposes actions such as collect, sell, buy, and spend.

Persistence via the useGamePersistence hook backed by Upstash Redis

Persistence is provided via the useGamePersistence hook, which saves and loads game state through the /api/game/[id] route. The route is backed by Upstash Redis.

Auto-save events

Auto-save triggers on the following game events:

  • resource collection
  • selling
  • buying
  • station repair

Headless GameSimulation mirrors scene.ts orchestration

A headless GameSimulation mirrors the scene.ts orchestration for integration testing. It uses the same tick function that scene.ts uses, so the simulation and the rendered game stay in sync.
